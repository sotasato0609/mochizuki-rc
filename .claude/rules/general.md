# 共通ルール

## 自動実行

### 🛑 自動発火してはならないスキル

**`/campaign-create` `/adgroup-create` `/ad-create` `/keyword-create` は Claude が自動で発火させない。** 実在の広告アカウントに書き込むため、`disable-model-invocation: true` を設定してある。

「キャンペーンを作って」「広告を作って」「キーワードを追加して」「出稿して」と言われても**勝手に実行せず、ユーザーに該当スキルを打つよう促す**。公式も副作用のあるスキル（`/deploy` 等）についてこの方針を推奨している（`.claude/skills/skill-authoring/reference.md` 第1節）。

許可リストが「**どこに**書くか」を守るのに対し、このフラグは「**いつ**発火するか」を守る。

### 広告運用（読み取り・提案系は自動発火してよい）

- キャンペーンの分析・数値の確認を依頼された場合 → `/campaign-analysis` スキルの手順に従う
- GA4・サイト内行動・フォーム離脱・流入の質の分析を依頼された場合 → `/ga4-analysis` スキルの手順に従う（読み取り専用）
- Meta（Facebook・Instagram）広告の実績分析を依頼された場合 → `/meta-analysis` スキルの手順に従う（読み取り専用）
- Google Ads 単体の実績分析を依頼された場合 → `/gads-analysis` スキルの手順に従う（読み取り専用）
- **媒体横断でまとめる場合** → `reporting-common/reference.md` の合算規律に従う。`collect.py` で取得する
- 広告文・クリエイティブの作成を依頼された場合 → `/creative-generation` スキルの手順に従う
- 入稿・広告の作成を依頼された場合 → `/ad-trafficking` スキルの手順に従う
- レポート作成・クライアント報告を依頼された場合 → `/ad-report` スキルの手順に従う
- 予算配分の見直しを依頼された場合 → `/budget-optimization` スキルの手順に従う

### 汎用

- コードレビュー・PR確認を依頼された場合 → `/pr-review` スキルの手順に従う
- プレゼン・スライド・資料作成を依頼された場合 → `/pptx` スキルの手順に従う

## 広告運用の鉄則

- **🛑 既存の顧客アカウントへの書き込みはデフォルト拒否。** MCC `5528496923` 配下の3,784件（うち稼働中863件）は顧客企業のアカウント。**CLAUDE.md の最優先ルールが全てに優先する**
- **MCC `5528496923` 自体の操作と、配下への新規アカウント作成は許可されている**（既存アカウントに触れないため）
- **書き込み対象は `accounts.md` の許可アカウントリストに載っているIDだけ。** リスト外なら API を叩く前に停止して聞く。Claude が自己判断でリストに追加しない
- **検証はテストアカウントで行う。本番で試さない**
- **配信設定・予算・入稿の変更は、対象IDが特定され、ユーザーが承認した場合に限り Claude が実行してよい。** 包括的な事前承認とは解釈しない
- **書き込み前に必ず `validate_only` で dry-run する**
- 数値を推測・創作で補完しない。データにない値は「データなし」と書く
- 広告プラットフォームの仕様は変わる。文字数・APIバージョンを記憶で書かず、`.claude/rules/ad-specs.md` と公式ドキュメントを確認する
- CV 30件未満の区分で効率を判断しない（統計的に無意味）

## 品質基準

- タイムゾーン: Asia/Tokyo
- コミット形式: `<type>(<scope>): <日本語説明>`
- type: feat / fix / refactor / docs / test / chore / ci
- 機密情報 → Secret Manager必須。.env禁止
- 非機密設定 → `config.json` で管理
- ライブラリ/フレームワークのAPIを使う実装では、Context7 MCPで最新ドキュメントを確認してから書くこと

## データの正確性・永続化

- 値を修正する時は `grep -r` で全ファイル検索し、コード・設定ファイルの全箇所を一度で完了させる
- 修正後にもう一度 `grep` して残りがないことを確認する
- データを推測・創作で補完しない。取得できなかった情報は空のまま残す
- ユーザーが伝えた数値・日付・ステータス・条件は、聞いたその場でメモリに永続化する
- 設計判断・ユーザー指示は CLAUDE.md またはメモリに即座に保存。コンテキスト圧縮前に重要情報を永続化する

## 成果物の正確性プロトコル（絶対厳守）

数字・主張を成果物に載せる**その瞬間**に以下を適用する。検証は後工程でなく作成に内包する。
`/pptx` をはじめ、レポート・提案書・スライドの全成果物に適用する。

### 1. スコープ先確定

分析前に対象の母集団を必ず列挙する（例：どのアカウント・プロパティ・期間が対象か）。「全件」「一極集中」「全額」「最大の」等の総括語は、母集団を実際に数え上げた場合のみ使用可。スコープ変更時は依存する全数値を再導出する（旧値の使い回し禁止）。

### 2. 数値は出所タグ付きで一度だけ定義（Single Source of Truth）

各数値に「出典・取得日・分母・スコープ」を紐付ける。同じ数値は資料内で一箇所に定義し、全箇所で同一表記。分母の異なる%を同一文に並べない。

### 3. 一次資料を開いて引用

外部・財務・競合・IR数値は、記憶やエージェント要約でなく**一次資料（IR PDF・公式PR・政府統計の原本）を開き、原文の文言・期・主体を確認**してから記載。原文を変形しない。主体（単体/セグメント/連結）を必ず明記。

### 4. 両面提示を既定（片面提示＝虚偽扱い）

ある指標を出す時は反する事実を同じ場所に併記する。有利・不利の一方だけの提示は禁止。「帰属不能」と認めた事項を別の場所で成果として断定しない。

### 5. 証拠クラスの明示

各主張に〈実測(出典)／業界一般(出典)／当社仮説〉のラベルを付与する。仮説・一般論を実測事実のように書かない。注記（未実測・試算・要確認）は数値と一体で**全出現箇所に伝播**させる。

### 6. 内部整合性パス（確定前必須）

繰り返し登場する数値・スコープ表記・ステータス（済/未）が全ページで一致するか照合する。矛盾を残さない。

### 7. 口頭補足前提の排除

成果物だけを読む相手が字面で誤読しないか確認する。口頭でしか守れない断定は書かない。図は不利・有利指標の片方だけを可視化しない。

### 8. 対外/社内の分離

提出版は社員名・競合の財務断定・未検証値を除去する。社内たたき台と提出版を混在させない。

> **🛑 本プロジェクト固有の追加規律**：提出版に**原価・粗利・マージン率・媒体実費（API実測の消化額）を一切載せない**。
> 請求額と並べるとマージンが逆算されるため、CPC・CPMも請求額ベースで再計算する。社内版は `*.local.md`（gitignore対象）に分離する。

### 9. 完了報告前の敵対的検証

自作物を自分で「問題ない」と言わない。`fact-checker` エージェントで各主張を「反証する」立場から検証し、各数値を一次出典まで遡って確認してから報告する。

## フィードバックループ（実装→検証サイクル）

実装後は以下の検証チェーンを**全て通過するまでループ**する。途中で失敗したら修正して再実行。通過前に完了報告しない。
このプロジェクトは静的LP（HTML/CSS/JS）+ Cloud Functions(Node) 構成のため、TypeScript / vitest / Cloud Run は使わない。

```
実装 → Prettier整形 → (functions変更時) node --check 構文チェック → (UI変更時) Playwright MCP でビジュアル検証 → 完了
  ↑                                                                                              ↓
  └──────────────────────── 失敗 or 崩れ発見 → 修正して再実行 ←─────────────────────────────────┘
```

- 同じ修正を2回繰り返したら、アプローチを変えて根本原因を特定する
- Cloud Functions（`functions/index.js`）を変更したら `node --check` で構文を確認する
- HTML/CSS/JS を変更したら `npx prettier --check <file>` でフォーマットを確認する（Stopフックが自動で弾く）
- UI変更時のビジュアル検証手順は `.claude/rules/frontend.md` に定義

## 並列開発

複数の独立タスクを同時に進める場合 → `parallel-dev` ワークフローを実行する。
各タスクは git worktree で隔離され、個別ブランチで並列実装→検証→PR作成まで自動で進む。

## コンテキスト管理

**自動Compaction禁止。** コンテキスト圧縮は細部の欠損を招くため、Compactionに頼らずセッションを管理する。

### 基本方針

- 新しいタスクに着手 → `/clear` してから要件を伝える（前タスクのノイズを排除）
- 同じ修正を2回以上繰り返している → `/clear` して正解だけ伝えてリスタート
- 調査タスク → メインコンテキストを汚さないようサブエージェントに委譲してよい。**ただし公式ドキュメントの調査は例外で、`WebFetch` で自分で引く**（`researcher` は3回連続で空振り。`.claude/rules/api.md` 参照）
- 設計判断・ユーザー指示 → 発生した時点でメモリに永続化する

### コンテキスト枯渇時のセッション引き継ぎ

コンテキストウィンドウの消費が大きくなってきたと判断した場合（大量のファイル読み込み、長い実装ループ、複数タスクの連続処理）、以下の手順で新セッションへの引き継ぎを行う:

1. **作業を区切りのいいところで止める**（中途半端なファイル編集を残さない）
2. **引き継ぎドキュメントを作成** → `.claude/handoff.md` に以下を網羅的に記録:
   - 完了したタスクとその成果（変更ファイル・コミットハッシュ）
   - 未完了タスクと残作業の詳細
   - このセッションで下した設計判断とその理由
   - 発見した問題・ブロッカー
   - 次セッションで最初にやるべきこと
3. **未コミットの変更があればコミットする**（引き継ぎドキュメント含む）
4. **ユーザーに報告**: 「コンテキストが逼迫しています。引き継ぎドキュメントを `.claude/handoff.md` に作成しました。新しいセッションで `/clear` 後に `cat .claude/handoff.md` で文脈を復元してください」と伝える

### 引き継ぎドキュメントの検証

引き継ぎドキュメント作成時、以下を自己チェックする:

- [ ] 未完了タスクが漏れなく列挙されているか
- [ ] 変更したファイルのパスが全て記載されているか
- [ ] 設計判断の「理由」が書かれているか（結論だけでは次セッションで再議論になる）
- [ ] ユーザーから受けた指示で、メモリに保存していないものがないか
- [ ] 次セッションの最初のアクションが明確か
